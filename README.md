# event-broker-api
RESTful API сервис для управления мероприятиями (событиями) с полным CRUD функционалом.

## 📋 Описание
API позволяет создавать, читать, обновлять и удалять мероприятия. Также формировать бронь на мероприятие, читать и обрабатывать ее. Каждое событие содержит информацию о названии, времени проведения, описании и информацию о бронировании на него.

## 👤 Пользователи (ролевые модели Domain.Models.Role)
1. Группа **Admin** - администраторы сервиса. Доступ не ограничен.
2. Группе **User**  - непосредственные клиенты сервиса. Управление собственным бронированием не мероприятие.

*Текущая реализация контроля (на уровне сервисов)*
•	Неаутентифицированный пользователь (ICurrentUserService.IsAuthenticated == false) не может создавать брони. Создавать бронь, смотреть свои брони — для аутентифицированных пользователей.
•	Отмена брони (BookingService.CancelBookingAsync): разрешена владельцу брони (currentUser.UserId == booking.UserId) или Role.Admin.

*Получение JWT‑токена через Swagger (инструкция)*
Предварительно В Swagger UI, используя, API POST /auth/register, зарегистрируйте пользователя. Если он создан переходите к пункту 4
1. В теле запроса отправьте JSON c полями UserName, Password, Role
2. Значения Role: Admin - "1", User - "0"
3. Ответ bool - значение с результатом регистрации. При значении true. 
4. В Swagger UI выполните вызов API авторизации POST /
5. Найдите операцию получения токена (по имени контроллера/эндпоинта, например POST /auth/login). Проверьте, какой маршрут соответствует использованию UserLoginDTO.
6. В теле запроса отправьте JSON с полями UserName и Password (имена из UserLoginDTO)
7. Из ответа скопируйте JWT токен.
8. В Swagger UI сверху справа нажмите кнопку Authorize, в модальном окне в поле Value введите: **Bearer <JWT-токен из предыдущей операции>**, нажмите 

**JWT использует секрет для формирования подписи. Он хранится в appsettings.json. Для продакшена настоятельно рекомендуется хранить этот ключ в переменных окружения или 
в предназначенных для этих целей сервисах**

## 🧰 Функциональность
| Метод | URL | Описание | Payload |
|-------|-------|-------|-------|
| **GET**         | /events |получение списка всех событий           |-|
| **GET**         | /bookings/{bookingId:guid} |получение информации о бронировании на событие           |-|
| **DELETE/{id}**   | /bookings/delete/{booking:guid} | удаление (полная отмена, даже утвержденной брони | доступна Администратору |
||*Параметры фильтрации*||
| **GET/{id}**    | /events/{id:guid} |получение события по идентификатору |-|
| **POST**        | /events |создание нового события |json модель события (см ниже)|
| **POST**        | /events/{eventId:guid}/book |создание неподтвержденного бронирования на мероприятие |json модель бронирования (см ниже)|
| **PUT/{id}**    | /events/{id:guid} |полное обновление существующего события |json модель события (см ниже)|
| **DELETE/{id}** | /events/{id:guid} |удаление события |-|
|-------|-------|-------|-------|
|**POST** | /auth/register | регистрация пользователя | json объект пользователя (см ниже)
|**POST**| /auth/login | авторизация пользователя | json объект пользователя (см ниже)

**примечание** 

Теперь вызов метода создания бронирования **POST** /events/{eventId:guid}/book связан с кол-вом свободных мест.
Если очередной запрос брони на мероприятие превысит это кол-во вернется ответ **409 Conflict**

### Параметры фильтрации метода GET
|параметр|тип|описание |примечание|
|-------|-------|-------|-------|
|Title|string|Фильтр по названию события|частичное совпадение, не зависит от регистра|
|From|string|Начало события|включительно (формат ISODateString)|
|To|string|Конец события|включительно(формат ISODateString)|
|ValidatePeriod|boolean|Включить проверку|что начало раньше завершения события,|
|Page|int|Номер страницы| **по умолчанию 1** (*** обратите внимание ***)|
|PageSize|int|Количество записей на странице| **по умолчанию 10** (*** обратите внимание ***)|
|OrderBy|string|Сортировка результатов| не реализовано|

***пример запроса события***

**GET /events**?Title=конференция&From=2026-05-01T00:00:00Z&To=2026-05-31T23:59:59Z&ValidatePeriod=true&CheckPeriod=false&Page=1&PageSize=20&OrderBy=date%20desc

***пример бронирования на мероприятие***

**Сервис обработки бронирования** - отдельный фоновый процесс, ускоряющий UX работы с API

use case прост (с возможным овербукингом):
1. выполнив запрос на создание события **POST /events**, вы получите 201 c location, содержащим уникальный id (guid) только что созданного события
2. выполните запрос на создание неподтвержденной брони на вышеуказанное событие **POST /events/{eventId:guid}/book**. Если очередной запрос брони на мероприятие превысит это кол-во доступных мест вернется ответ **409 Conflict**
4. получив на клиенте 202 ответ, что бронь сформирована, вы также получите location на созданную бронь
5. периодически опрашивайте **GET /bookings/{bookingId:guid}** API о созданной брони, чтобы получить более подробную информацию о ее текущем статусе (что она подтверждена или отменена)

** примечание **

Применены примитивы синхронизации для защиты от непредсказуемых результатов и обеспечения целостности данных при состоянии гонки или попытки овербукинга:
1. *lock (_lockObject)* - гарантирует, что только один поток одновременно может находиться внутри защищенного блока кода и работать с переменными в нем. **Нельзя использовать с async/await**
2. *SemaphoreSlim* - ограничение количества одновременно выполняемых асинхронных операций. Метод WaitAsync не блокирует поток — позволяет эффективно ждать в асинхронном коде.

## 🏯 Архитектура
Приложение построено по принципам Clean Archtiecture. И организовано на проектах-слоях:
- **Domain.csproj** - ядро системы (хранение бизнес-сущностей) системы обработки мероприятий (Event и Booking)

- **Application.csproj** - содержит контракты к системе доступа к данным и сервисов (и реализации этих контрактов) (usecases') приложения, также фоновая обработка бронирования на мероприятия
- **Presentation.csporj** - точка входа в приложение, конфигурирование DI, запуск миграций и енд-пойнтов (контроллеров) прилодения
----------------
- **EventBrokerAPI.IntegrationTests.csproj** - интеграционные тесты
- **EventBrokerAPI.Test.csproj** - unit-тестирование

### Измененен контекст данных приложения.
API использует docker-контейнер СУБД PostgreSQL (Unit-тесты API используют UseInMemoryDatabase имитацию, Интеграционные - контейнерную реализацию на Testcontainers)
Управление схемой БД осуществляется через **механизм миграций**. Реализовано их **автоматическое применение при запуске** основного приложения API и интеграционных тестов его репозиториев.
Поэтому ручное обновление схемы БД запуском команды **dotnet ef database update** также доступно, но необязательно.

## Выполните развертывание контейнера СУБД (для Windows)
1. активируйте компонент WSL (Windows Subsystem for Linux). В терминале (или оболочке powershell) выполните **wsl --install**
2. перезагрузите компьютер
3. скачайте и установите приложение **Docker Desktop** для Windows. (Установка дистрибутивов Unix не требуется)
4. проверьте, что процесс docker-daemon в работе **docker --version** или **docker ps**
    
## Клонирование репозитория API
1. откройте терминал
2. клонируйте проект **git clone -b sprint_8 https://github.com/SerikovGennadiy/event-broker-api.git**
3. перейдите в директорию **cd event-broker-api (содержащую sln файл решения)**
5. выполните **docker compose up -d** (команда ищет по умолчанию файл конфигурации и выполняет развертывание и запуск контейнера c СУБД PostgreSQL)
6. выполните **docker ps --filter "name=eventapi-postgres"** (убедитесь, что контейнер работает, тоже самое можно легко проверить, Docker Desktop)
