# event-broker-api
RESTful API сервис для управления мероприятиями (событиями) с полным CRUD функционалом. Построен на базе микросервисной архитектуры с исполбзование бровера сообщений Kafka

## 📋 Описание
API позволяет создавать, читать, обновлять и удалять мероприятия. Также формировать бронь на мероприятие, читать и обрабатывать ее. Каждое событие содержит информацию о названии, времени проведения, описании и информацию о бронировании на него.

## 👤 Пользователи (ролевые модели EventBroker.Contracst..Enums..Users.Roles)
1. Группа **Admin** - администраторы сервиса. Доступ не ограничен.
2. Группе **User**  - непосредственные клиенты сервиса. Управление собственным бронированием не мероприятие.

*Текущая реализация контроля (на уровне сервисов)*
•	Неаутентифицированный пользователь (ICurrentUserService.IsAuthenticated == false) не может создавать брони. Создавать бронь, смотреть свои брони — для аутентифицированных пользователей.
•	Отмена брони (BookingService.CancelBookingAsync): разрешена владельцу брони (currentUser.UserId == booking.UserId) или Role.Admin.

*Получение JWT‑токена и тестирование API через Scalar (инструкция) (http://localhost:5000/scalar*

Предварительно В Scalar, используя, API POST /auth/register, зарегистрируйте пользователя. Если он создан переходите к пункту 4
1. В теле запроса отправьте JSON c полями UserName, Password, Role
2. Значения Role: Admin - "1", User - "0"
3. Ответ bool - значение с результатом регистрации. При значении true. 
4. В Scalar выполните вызов API авторизации Users/Auth API /auth/login
6. В теле запроса отправьте JSON с полями UserName и Password (имена из UserLoginDTO)
7. Из ответа скопируйте JWT токен.
8. В Scalar сверху слева будет select для доступа к API микросервисов
9. Для Bookings и Events справа форма настройки запросов в поле **Bearer** введите только полученный JWT-токен

**JWT использует секрет для формирования подписи. Он хранится в appsettings.json каждого микросервиса. Для продакшена настоятельно рекомендуется хранить этот ключ в переменных окружения или 
в предназначенных для этих целей сервисах**

**Сервис обработки бронирования** - отдельный фоновый процесс, ускоряющий UX работы с API

use case прост (с возможным овербукингом):
1. выполнив запрос на создание события **POST /events**, вы получите 201 c location, содержащим уникальный id (guid) только что созданного события
2. выполните запрос на создание неподтвержденной брони на вышеуказанное событие **POST /bookings/book/{eventId:guid}**
   Если очередной запрос брони на мероприятие превысит это кол-во доступных мест вернется ответ **409 Conflict**
4. получив на клиенте 202 ответ, что бронь сформирована, вы также получите location на созданную бронь
5. периодически опрашивайте **GET /bookings/{bookingId:guid}** API о созданной брони, чтобы получить более подробную информацию о ее текущем статусе (что она подтверждена или отменена)

## Flow BookingConfirmed
1. Микросервис **Bookings** отправит в шину сообщение **BookingStarted** с метаданными операции). 
2. Далее микросервис **Events.API**, подписанный на топик **event-booking** прочитает его, вызовет доменное событие уменьшения доступных мест, и отправит сообщение SeatReserved.

## 🏯 Архитектура
Приложение построено по принципам Clean Architecture и организовано как микросервисы (решение `event-broker-api.sln`):
- **EventBroker.Services/Users**, **Events**, **Bookings** - независимые сервисы, каждый со слоями Domain / Application / Infrastructure / Presentation

- **EventBroker.API** - API-gateway (YARP) с агрегированной OpenAPI/Scalar-документацией
----------------
Монолитные проекты `Application`, `Domain`, `Infrastructure`, `Presentation` удалены из репозитория (код перенесён в `EventBroker.Services` и `EventBroker.Contracts`). Вместе с ними удалены старые тестовые проекты `EventBroker.Tests` (были привязаны к коду монолита и не входили в sln).

## 🗄 Кеширование (Events + Redis, паттерн Cache-Aside)

Чтение событий (`EventRepository`) идёт через Redis. Логика живёт в репозитории: сначала проверяется кеш, при промахе данные берутся из PostgreSQL и кладутся в кеш с TTL.

| Ключ | Данные | TTL (из конфига) | Инвалидация |
|------|--------|------------------|-------------|
| `event:{id}` | событие по id (`GET /events/{id}`) | `Redis:EventTtlMinutes` (по умолчанию 5 мин) | **инвалидация при записи** — ключ удаляется после каждого изменения события |
| `events:top10` | топ-10 по проценту проданных мест (`GET /events/top`, формула `(total_seats - available_seats) / total_seats`) | `Redis:TopEventsTtlMinutes` (по умолчанию 1 мин) | **только TTL, без инвалидации** |

**Обоснование стратегии.** Топ-10 — рейтинг: минутное устаревание некритично, а сносить ключ на каждом бронировании (самый частый кейс изменения `AvailableSeats`) было бы избыточно. Для отдельного события устаревание заметно, поэтому выбран подход «инвалидация при записи», а не «обновление при записи»: он проще и исключает риск закэшировать незафиксированное состояние — удаление идёт строго после `SaveAsync`, следующий читатель сам прогреет кеш. Инвалидация покрывает все пути изменения, включая Kafka-обработчик (`ReserveSeats`/`ReleaseSeats` меняют `AvailableSeats` и тоже чистят `event:{id}`); при создании и удалении ключ корректно отсутствует/сносится. Сущность из кеша прикрепляется к `ChangeTracker` (`Attach`), иначе изменения на закэшированной копии молча не сохранялись бы.

**Деградация без ошибок.** Кеш — не источник истины: при недоступности Redis ошибки логируются (`ILogger`, уровень Warning), но не пробрасываются клиенту — запрос прозрачно идёт в PostgreSQL, прогрев/инвалидация пропускаются (устаревшее истечёт по TTL).

**Конфигурация.** Секция `Redis` в `appsettings.json` events-сервиса: `ConnectionString` (локально `localhost:6379`), `EventTtlMinutes`, `TopEventsTtlMinutes`. В Docker строка подключения задаётся переменной окружения `Redis__ConnectionString=redis:6379` (по имени контейнера, не localhost) — она переопределяет значение из JSON. Контейнер `eventapi-redis` (`redis:7.2-alpine`) описан в `docker-compose.yml` с healthcheck и томом `redis_data`.

4. проверьте, что процесс docker-daemon в работе **docker --version** или **docker ps**

## Тестирование
Проект `EventBroker.Tests/Events.Tests.csproj` (xUnit + Moq + EF InMemory), запуск:
1. выполните **dotnet test ./EventBroker.Tests/Events.Tests.csproj**

Фикстура `EventsFixture` поднимает изолированную InMemory-БД и словарный фейк Redis-кеша (с фиксацией TTL и удалённых ключей). Покрыты сценарии Cache-Aside:
1. попадание в кеш — репозиторий (БД) не вызывается (`event:{id}`, `events:top10` при пустой БД);
2. промах — данные берутся из БД и сохраняются в кеш с корректным TTL; топ упорядочен по проценту продаж;
3. мутации — инвалидация `event:{id}` на Update/Delete/Reserve/Release (оба Kafka-пути), `events:top10` при этом не сносится (стратегия TTL-only), на Create инвалидации нет;
4. битая запись в кеше — откат к БД с перезаписью.

## Запуск API
1. убедитесь, что порты, указанные в настройках запуска и `docker-compose.yml`, свободны
2. выполните **docker compose up -d --build** (команда ищет по умолчанию файл конфигурации, выполняет развертывание и запуск, подниимает в нужном порядке Kafka, PostgreSQL, микросервисы и API-gateway)
3. в терминале в конце вывода развертывания увидите микроотчет по состоянию всех контейнеров, дождитесь отработки их healthcheck проверок
4. В браузере при работе со Scalar/OpenAPI периодически выполняйте перезапуск с очисткой кеша браузера **Сtrl-F5**
